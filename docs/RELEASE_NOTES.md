# VASYA GNS LAB 1.1.0 — Release notes (2026-10-29)

## New
- **Graphical manager (PySide6)**, RU/EN, light/dark/system themes: Home, 8-step install wizard with a change preview,
  Catalog (186 components), Verify (incl. runtime create/start/console/stop), Repair, 4-step Uninstall wizard,
  Log, Diagnostics, Tools, Lab demos. Errors are shown as code + plain explanation + state + next action.
- **Complete Lab mode**: VASYA's own gns3server 2.2.61 inside the VASYA folder (own port, config, XDG dirs), bundled
  for Python 3.10–3.13 — your existing GNS3 is not touched. Integration and Selective modes kept.
- **Automatic downloads, no images in the release**: every public device image, the helper programs (Dynamips,
  uBridge, VPCS) and the Qt xcb libraries are downloaded from their upstream sources on first use and checked
  against `third_party.lock` (URL + SHA-256). Docker images are pulled by pinned digest into VASYA's rootless podman.
  Cisco IOS and other vendor images come only from a private source you control (folder, private GitHub release or
  private HTTPS URL; see docs/PRIVATE_IMAGES.md). A missing image marks only that device "image not available".
  `vasya fetch [--dry-run] [--docker]` downloads without installing.
- **One-file Linux delivery**: archive split into < 100 MB parts for Google Drive + `Setup.sh` that finds, verifies
  (sha256, cached) and unpacks them — also from Drive's ZIP downloads. No manual joining.
- **Payload import** (Home → Import images / `vasya import-payload`) — imports images from a private offline bundle,
  atomically.
- **Windows Setup.exe** (NSIS, per-user, embedded Python 3.12 + PySide6) — **UNVERIFIED** on real Windows.
- **Remote compute**: templates/images on a GNS3 VM for Windows hosts.
- **VPCS 0.8.5, Dynamips 0.2.25, uBridge 1.0.1** and the **xcb libraries** for Qt are downloaded and placed only when
  missing system-wide (`vasya gui-deps`, `vasya fetch`).
- **System-package receipts**: packages installed for VASYA after your approval are recorded with their before-state;
  full uninstall offers to remove only those that were not there before and have no other dependants.
- **Docker on Linux = rootless podman under the VASYA folder, on by default** (tested on Pop!_OS 24.04): VASYA writes the
  config (XDG, `netns="none"`), starts/stops its own `podman system service`, passes `DOCKER_HOST`/`VASYA_DOCKER_*`
  only to its gns3server, and pulls each image by pinned digest (or restores it from a verified offline archive).
  Bundled gns3server carries a tested 3-part patch (`VASYA_DOCKER_SOCKET`, attach/ws→attach fallback,
  `VASYA_DOCKER_FIX_UID/GID`). Shared Docker daemon only on explicit choice. Windows Docker via GNS3 VM — UNVERIFIED.
- **Isolated GNS3 GUI profile**: installer writes VASYA's own `gns3_gui.conf` (inside the VASYA folder)
  with the Wireshark live-capture command, the vncviewer console command and the VPCS path; your own keys are kept.
- **KVM probe**: KVM is enabled for VASYA's server only if `qemu -accel kvm` actually starts.
- **Known external side effects** (`~/.vnc` from vncviewer) are recorded and listed in the uninstall report.

- **Docker images pinned**: all 21 Docker appliances (20 unique images) are pinned to the registry
  digest + image ID that were archived and tested (`data/docker-images.json`, generated by
  `scripts/import_docker_archives.py`); a pull or restore whose image ID differs from the pin is refused.
- **Optional Docker image pack** (offline alternative) `VASYA-GNS-LAB-1.1.0-Docker-Images` (`scripts/build_docker_pack.py`: archives
  hardlinked, tar streamed into 95 MiB parts, own parts.json + SHA256SUMS). Linux Setup.sh auto-detects, verifies,
  joins and unpacks it into `<VASYA>/Images/docker` (only pinned files, each sha256-checked; damaged part → exit 7,
  nothing placed). Absent → images are pulled instead.

## Fixed (Docker appliances, with regression tests)
- **gns3server patch 4** (`gns3server-2.2.61-vasya-init-su.patch`): the container `init.sh` no longer
  runs busybox `su` when the container user is root (old-glibc images crashed: aaa, python-go-perl-php, exit 139).
  Applied to all bundled py310..py313 copies, mode kept; non-root users still use `su`.
- python-go-perl-php: default name `PythonGoPerlPHP-{0}` (the upstream name gave gns3server 409).
- stonework: empty start_command (the upstream startup script is gone from the current image); the image CMD runs.
- turnkey-wordpress: opt-in preseeded first boot (`VASYA_TURNKEY_PRESEED=1`) — **UNVERIFIED**, see KNOWN_ISSUES 14.

## Fixed (found by running 1.0.1 on Pop!_OS 24.04; with regression tests)
- **Appliance fixes merged** (templates fixed by hand and tested): the fixes are baked into the shipped `.gns3a` files
  and into the templates VASYA creates, so a fresh install is already fixed (tests compare with the fixed templates
  field by field):
- D1: the "internet" appliance used a vde uplink → now `-net nic,model=e1000 -net user` (slirp); the node starts.
- D2: openwrt-realview used qemu-system-x86_64 → `qemu-system-arm -M realview-eb-mpcore`, initramfs as the kernel; missing emulator gives BLOCKED with the command.
- D3: puppy-linux, smoothwall, IPCop: blank 8 GB hda + ISO as CD-ROM, boot from CD, ≥ 512 MB RAM; boots (runtime PASS).
- D5: big images are hardlinked (else symlinked), never auto-copied.
- D6: rollback/uninstall never delete by name — only receipted resources whose sha256/size still match. The 1.0.1
  hotfix's 12 ownership checks are kept as regression tests.
- D7: pre-existing residue outside the VASYA folder is reported, not deleted.
- GNS3's builtin blank disks (`empty*G.qcow2`) are recognised as equivalent instead of a name conflict.
